# 组件审计

使一个组件的内置文案、主题能力和公开文档与实际源码准确一致。以当前工作区为事实依据，并确保每一处改动都能归因于目标组件。

## 确定范围

- 目标必须是一个组件目录或一个公开组件族。如果请求包含多个互不相关的组件，请用户先选择其中一个。
- 只有当桌面端/移动端变体、子组件、针对性测试、集中 locale 数据和 README 属于同一公开组件族时，才将它们纳入目标范围。
- 先检查 `git status`，保留用户的无关改动，尤其是共享 locale 和 theme 文件中的改动。
- 将“审核”“核对”类请求视为只读任务。只有用户要求修改、补全、迁移或修复组件时才编辑文件。
- 当相邻组件的当前实现与共享规范或目标组件的公开 API 冲突时，不要将相邻组件作为事实依据。
- 新增共享 theme token、改变翻译器行为、使用共享 locale 命名空间或编辑其他组件，都属于跨组件决策。先说明必要性并取得用户指示，再扩大任务范围。

## 决策前阅读

检查目标组件的实现、props、emits、slots、exposed/static methods、exports、测试、examples、样式、移动端对应实现和当前 README。然后阅读以下三份项目规范：

- [Locale 规范](references/locale.md)
- [Theme 规范](references/theme.md)
- [README 规范](references/readme.md)

使用源码和测试判定文档描述是否成立。README 只能作为设计意图的证据，不能证明当前行为。保持当前公开 API；不要仅因旧 README 提及某项 legacy API 就将其恢复。

## 审计与实施

1. 盘点目标组件中由组件库提供、面向用户的文案，判断哪些字符串需要 locale key。
2. 盘点桌面端/移动端样式和渲染代码中可主题化的视觉值，区分语义化 UI 值与刻意固定的图形色或数据色。
3. 将 README 与实际公开 API 和可运行行为逐项比较。
4. 需要实质性改动时，先给出简洁的组件级计划。
5. 在 locale、theme、实现、测试和 README 之间做最小且完整的改动。只移除因本组件改动而过时的残留。
6. 完成后再次审计目标组件，检查 locale key 对齐、硬编码 theme 残留、桌面端/移动端一致性、README 过时描述以及 legacy `:::RUNTIME` 容器。

不要强制修改 locale、theme 和 README 三项中的每一项。某项已经正确或不适用时，保持不变并说明依据；实际改动可以是零项、一项、两项或三项。

## 验证

- 对只读审计，如果非变更性检查能实质增强结论，就按风险执行适量检查；只读模式禁止编辑，不禁止验证。
- 对实施任务，根据实际改动面选择检查，不要只为满足清单而运行无关测试套件。
- 当目标存在针对性测试或组件行为发生变化时，通过仓库脚本运行组件测试：`npm run test -- --package-name components --subpackage <directory> --no-coverage`。如果筛选结果为零个测试，明确报告并改用其他相关检查；绝不能将其作为测试通过的证据。
- 当相应文件类型发生变化时，对改动过的源码、examples 和 README 运行针对性的 ESLint/Stylelint 检查。
- 翻译器行为或集中语言数据发生变化时，运行 locale 相关测试。
- theme 代码发生变化时，除了 Stylelint 还要编译受影响的 SCSS 入口；lint 不能证明 Sass 函数和 import 能正确解析。
- TypeScript 公开类型、props、emits、exposed methods 或 imports 发生变化时，运行 typecheck。
- 使用 `npm run docs:dev` 预览 README 的页面结构、文案和 Playground 展示。根 `index.html` 将 `@deot/vc` 映射到已发布的 CDN 资源，因此不得将 `docs:dev` 的结果作为本地组件源码修改已生效的证据。
- 需要在浏览器中调试或验证当前组件源码、交互或可见 theme 行为时，使用 `npm run dev`；theme 值变化时检查亮色和暗色主题。同时涉及文档和本地源码时，按各自职责分别使用两个命令。
- 最后运行 `git diff --check`，进行范围明确的 diff 复核，并检查 `git status --short`。
- 将目标范围内的成功结果与无关基线失败或环境失败分开报告。

## 延续新决策

用户可能在此 Skill 执行期间修正规范。即使用户的当前指示与本 Skill 冲突，也要将用户的当前指示应用到目标组件。

将每项修正或新发现的不一致归为以下一类：

- **组件特有规则：** 只影响当前组件；不要更新 Skill。
- **可延续的项目规则：** 应指导后续组件任务、与 Skill 冲突，或补足了会重复出现的规则缺口。

对于可延续的项目规则：

1. 说明依据、对后续任务的影响，以及应修改的具体 Skill 文件和规则。
2. 提议最小的措辞改动，并明确询问是否更新 `component-audit`。
   示例：`这条修正会影响后续组件：<规则>。是否同步更新 references/<area>.md？`
3. 能安全继续的组件工作照常进行；结果依赖尚未确定规则的工作则先暂停。
4. 未经用户明确同意，绝不在常规组件任务中编辑本 Skill。
5. 获得同意后，只更新相关 instruction/reference，运行 Skill validator，并在最终 diff 摘要中列出 Skill 改动。
6. 如果用户拒绝或没有回应，不要持久化该提议；只有后续任务仍会受影响时，才将其列为待定事项。

不要累积一次性例外。只有用户明确作出决定，或有重复且由源码支持的证据时，才将规则泛化。

## 交付

对于只读审计，分别将 locale、theme 和 README 标为 **已对齐**、**需要修改** 或 **不适用**。提供源码依据、具体不一致、最小修复建议，以及已运行或跳过的检查和原因。

对于实施任务，报告：

- locale/theme/README 的改动，包括有意保持不变的部分；
- 针对性验证命令和准确结果；
- 无关失败或尚未经过浏览器验证的行为；
- 仍在等待批准的可延续 Skill 更新提议。
